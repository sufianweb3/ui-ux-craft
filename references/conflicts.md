# Where experts disagree, and the default this skill uses

Taste includes knowing when rules conflict. Follow the default unless the product's context says otherwise, and when you deviate, say why. Entries 1–18 are the round-2 rulings (binding, October 2026); 19 onward are other recorded disagreements. Source short-names are in `sources.md`. Every skill file applies these defaults the same way; if a reference file seems to disagree, this file wins.

## Round-2 rulings

| # | Topic | Positions | Default here |
|---|---|---|---|
| 1 | **Capitalisation** | Microsoft: sentence case everywhere. Mailchimp: title case for page titles and global nav. Apple HIG: title case for buttons, menu items, segment labels, column and (since Liquid Glass) list section headers; sentence case for alert buttons. Apple Style Guide: write element names exactly as they appear. | Follow the project's existing convention first. Otherwise sentence case for web/SaaS; HIG title case for buttons, menus and section headers in native Apple-platform UI. Never all caps. One case style per element type. |
| 2 | **Error copy and "we"** | Apple HIG Writing: "avoid using *we* altogether" ("Unable to load content"). Apple Style Guide: no first person, no "please". HIG Inclusion: reserve "we" for the company. Mailchimp/Microsoft voices allow a friendly "we". GOV.UK/NN/g: say what happened and how to fix it. | No "we", no blame, no "please" in error and system messages. State what happened and how to fix it: "Couldn't save changes. Check your connection and try again." "We" only where the company itself speaks (emails, policies). |
| 3 | **Validation timing and disabled submit** | Silver, GOV.UK: validate on submit. Wroblewski: blur beats keypress. Baymard: blur, then live once an error shows. Apple HIG Entering data/Text fields: validate as soon as data is entered; enable Next/Continue only after required data is present; email on blur, username/password live. Apple-via-Emil (secondhand WWDC26 distillation): "validate inline, not on submit". Silver/Vercel: never pre-disable submit. Hurff: an empty chat "Send" can be disabled. Figma: disabled + explanation is fine. | Web: validate on submit, then on blur/live once a field has been touched and errored; clear an error as soon as it's fixed; never on focus. Keep submit enabled (exception: a single-field composer). Native Apple apps may follow HIG and disable Continue until required data is present. Never use `pointer-events: none` on disabled controls (it kills the reason tooltip); always explain why a control is disabled. |
| 4 | **Animation duration** | Emil: routine UI < 300ms; press 100–160, tooltip 125–200, dropdown 150–250, modal ~250, drawers up to 500ms (drawer curve), Sonner toasts 400ms `ease`. NN/g: 100–400ms (500 for drag). M3 springs: 350–750ms spatial. Figma: button states 100–200ms. Apple 227: shorten delays and stagger when tuning. | Frequent micro-interactions 100–200ms; menus, popovers and modals 150–250ms; large surfaces travelling far (drawers, sheets) up to ~500ms; toasts may enter in ~400ms. Anything seen hundreds of times a day: minimal or no animation. Long springs only for rare hero moments. (Replaces the old "nothing ≥ 400ms" rule.) |
| 5 | **Reduced motion** | Old skill snippet: blanket `0.01ms !important` override. web.dev: opt-in motion. Apple Reduced Motion criteria: remove decorative motion, replace meaningful motion with dissolve, highlight fade or colour shift; kill parallax, animated blur, spin, multi-axis, auto-advance. Emil: "fewer and gentler, not zero". | Remove decorative motion and replace meaningful motion with fade, dissolve or colour change. Don't blanket-kill all transitions or remove the feedback itself. The blanket override is a last-resort safety net only. Also honour `prefers-reduced-transparency` and `prefers-contrast: more`. |
| 6 | **Gradients** | Rams, anti-slop: decorative gradients date fast. Google Gemini design: gradients and animated forms are the core visual language for AI state. | Banned as decoration. Allowed only as an established brand asset, or as one deliberate, consistent signal of an AI/generative state (listening, thinking, generating) with a clear start and end and a reduced-motion fallback. Never generic hero, button or card decoration. |
| 7 | **Line length and line height** | Butterick: 45–90ch, leading 1.2–1.45. M3 Breakpoints: 40–60 characters per line. Figma: 40–60ch and leading 1.125–1.2 (heading values). Apple HIG: loose leading for long passages; tight only for 1–2 lines. | Body text 45–75 characters, aim ~66; 40–60 acceptable on narrow or mobile columns. Paragraph line-height 1.4–1.6; 1.1–1.25 only for headings and UI labels. If lines run long, increase line-height. |
| 8 | **Numbers in copy** | Microsoft and this skill: numerals ("3 projects"). Apple Style Guide: spell out one–nine in running prose, except units, time and same-category numbers > 9. | Numerals in UI (badges, tables, buttons, labels) for scannability. Apple's spell-out rule applies to prose only. Format with the user's locale (`Intl`). |
| 9 | **"Done" as a button** | Silver/Microsoft: outcome verbs, never "Done". Apple HIG Sheets: "Done" is the standard completion button, paired with Cancel or Back (never all three). | "Done" is fine as the standard confirm in Apple-style sheets and editors, paired with Cancel. Elsewhere prefer outcome verbs. |
| 10 | **Destructive dialogs** | APG: initial focus on the least destructive button. Apple HIG Alerts: Cancel never default; never bind Return to a destructive action the person didn't ask for; a deliberately chosen destructive action may be default and not red. Figma/Lowry: prominent red "Delete account", grey "Keep". | Focus the least destructive option. Enter never triggers the destructive action. Style the destructive button as destructive (red), but never as the default. |
| 11 | **Contrast thresholds** | WCAG 1.4.3: 4.5:1 text, 3:1 large (≥ 24px, or ≥ 18.66px bold). WCAG 1.4.11: 3:1 for visual information needed to identify components and states. Apple Accessibility Inspector treats any bold text as large. Apple HIG Dark Mode: strive for 7:1 on custom small text. M3: standalone FABs identified by their icon needn't meet 3:1 container contrast; clustered controls must. | WCAG wording: UI component boundaries and states needed to identify them 3:1; text 4.5:1, large 3:1. Bold does not make text "large" unless ≥ 14pt (18.66px) bold. Aim for 7:1 on custom dark-mode pairs where feasible. Grouped or segmented controls need ≥ 3:1 separation; a standalone control identified by its label or icon may have a lower-contrast container. |
| 12 | **Theme switch** | Apple HIG Dark Mode: "avoid offering an app-specific appearance setting". Web convention and Android Themes: offer an in-app override; never lock to light. | Follow the OS setting by default. If a theme switch exists, offer System (default) / Light / Dark and react live to OS changes. |
| 13 | **SF Pro tracking and Apple fonts** | Old skill text: "SF tracking goes from positive at small sizes to negative at large". Apple HIG Typography table: +41/1000em at 6pt, 0 at 12pt, negative 13–23pt (−26 at 17pt), positive again 24–76pt (peak +14 at 28–30pt), 0 at 80pt+. Emil (after Apple WWDC20) and community extractions: display tracking ≈ −2% to −4% at 48px+. | The SF table applies to SF only (negative 13–23pt, positive 24–76pt); never port it to Inter, Geist or others; follow each foundry's guidance. "Slightly negative tracking on large display text" stays as general practice, not an Apple rule. Don't ship SF fonts or SF Symbols in web apps (licensing). |
| 14 | **Light body weights** | This skill and Apple HIG: ≥ 400 for UI text, avoid Ultralight/Thin/Light. awesome-design-md extractions claim Stripe at 300 and Figma ~320 (variable custom faces). | Body weight minimum 400 stays. The awesome-design-md brand claims are unverified observations only and don't justify lighter weights. A brand's own published system may specify otherwise if legibility and contrast are verified at size. |
| 15 | **Figma resource-library claims** | Figma *Fitts' law*: screen corners ("magic pixels") are hard to reach, so put minor items there. Classic HCI: pointer-captured edges and corners are the fastest targets. Figma *Interaction design*: "Submit" is a clear label. Silver, Microsoft, Mailchimp: outcome verbs. | Both rejected. Edge-anchored desktop controls are fast to hit; on windowed web and touch, reach depends on cursor position and thumb zone. Use outcome verbs, not "Submit". |
| 16 | **Shortcut hints in menus** | NN/g and this skill: show shortcuts in menus to teach them. Apple HIG Context menus: omit shortcut hints. Eldh (Linear): context menus list nearly every action with its shortcut, as the mouse user's learning path. | Show keyboard shortcuts in app/dropdown menus, tooltips and the command palette. Context menus may omit them; show them there when the context menu is the product's main command surface. |
| 17 | **Hover** | M3 States: containers (app bars, dialogs, sheets, nav) get no hover; their actionable children do; only one element hovered at a time. Emil mobile-native: ungated `:hover` sticks on touch. NN/g, WCAG 2.5.7, Apple HIG Accessibility: hover-only and gesture-only actions exclude people. | Style items, not containers. Hover-only affordances only behind `@media (hover: hover)` (Emil adds `and (pointer: fine)`). Every gesture and hover-reveal has a visible control alternative. |
| 18 | **Sourced vs inferred rules** | Round-2 brief: every rule needs a source. Some rules are reasonable syntheses or web translations of native guidance. | Mark rules inferred rather than sourced as **[synth]**. Every new rule cites its source short-name; every source is listed in `sources.md`; community material is marked **[unverified]**. |

## Other recorded disagreements

| # | Topic | Positions | Default here |
|---|---|---|---|
| 19 | **Green success ticks** | Baymard: tick every field. Wroblewski: they confuse on easy fields. Silver: "format valid" isn't "accepted". | Only on hard fields (new password, username availability). |
| 20 | **Required vs optional markers** | Silver: mark only "(optional)". Baymard (checkout): mark both. Mailchimp: label required clearly. | Long or transactional forms: mark both. Short forms: optional only. Consistent within a product. |
| 21 | **Input masks** | NN/g (Slips) endorses live formatting. Silver: masks confuse. | Accept any format and normalise silently; light display formatting only, never blocking input. |
| 22 | **Undo vs confirmation** | Raskin: never warn when you mean undo. NN/g: confirmations as a safety net. Apple HIG Alerts: warn only when data loss is unexpected and irreversible. Apple Assistive Access: "always ask for confirmation twice" for hard-to-recover actions. | Undo for anything reversible; confirm only irreversible, unexpected or high-cost actions, naming the consequence. Apple's double confirmation applies only to its simplified accessibility mode. |
| 23 | **Error message placement** | Silver/GOV.UK: above the input. Wroblewski tested to the right. NN/g, Apple HIG Writing: close to the source. | Above the input, below the hint. Works on mobile; not covered by autofill. |
| 24 | **Exit easing** | NN/g: ease-in on exit. Emil: never ease-in in UI. | Ease-out for enter and exit. Ease-in only for things accelerating fully off-screen. |
| 25 | **CSS transitions vs springs** | Emil: CSS transitions retarget on interrupt, so prefer them over keyframes for toggled UI. Apple via Emil: CSS transitions can't inherit gesture velocity. | Transitions for state toggles; springs (critically damped by default) for anything a finger or pointer drags. |
| 26 | **Pressed scale** | Emil: `scale(0.97)` (range 0.95–0.98). Figma button states: `scale(0.98)`. | Either; pick one per system and tokenise it. |
| 27 | **Deliberate delay** | Laws of UX (Doherty): a delay can raise perceived value. Nielsen, Emil, Vercel: speed. | Speed. A labour-illusion delay only for rare, high-stakes results. |
| 28 | **Spinners vs skeletons** | Hurff: skeletons. Emil: fast spinners are fine. Vercel: show-delay + minimum visible time. Apple HIG: prefer determinate progress; never morph a spinner into a bar. | Skeletons for content areas; small fast spinners inside buttons; delay rules always; determinate progress once duration is known. |
| 29 | **Contrast algorithm** | WCAG 2.2 ratios (conformance). APCA preferred by Vercel, used by Radix. | Meet WCAG 2.2 AA; optionally also check APCA. |
| 30 | **Colour model** | Refactoring UI (2018): HSL. Stripe, Evil Martians, Linear: perceptual. | OKLCH. |
| 31 | **Hover/press technique** | Radix, Evil Martians: step the ramp or use relative colour. M3 States: `currentColor` state layer at hover 8%, focus 10%, pressed 10%, dragged 16%. | Both valid; pick one per system. State layers suit many container colours; ramp steps suit tightly tuned palettes. |
| 32 | **Radius scale** | This skill: 4 / 6–8 / 12 / 16 / full. M3: 0/4/8/12/16/20/28/32/48/full, buttons full by default. | Use the product's platform: M3 scale on Material products; otherwise the skill's smaller set (dense desktop UI favours small radii). |
| 33 | **Type scales** | Refactoring UI: establish a scale. Butterick: modular ratios are overrated. M3: Major Second (1.125) scale of 15 styles. | A hand-picked small scale (~5 styles in use); no strict ratio required. |
| 34 | **Token tiers** | Curtis, DTCG and this skill: primitive → semantic → component. Figma: two tiers unless a third is justified; no alias chains. | Two tiers by default; add a component tier when one role must differ per component. Semantic tokens reference primitives directly. |
| 35 | **Grids** | Refactoring UI: "grids are overrated". MDN, Curtis: grid systems. | Content-driven layout; 12-column grid for editorial and marketing; fixed sidebar + fluid content for apps. |
| 36 | **Spacing scale** | Curtis: doubling from 16. Common practice: 4px base. M3/Android: 8-unit layout grid, 4 for icons and type. | 4px base with a small non-linear set. The rule is "only scale values". |
| 37 | **Focus ring technique** | Pickering: box-shadow. Soueidan: outline (survives forced colours). APG: browser defaults. Figma: 3px + 3px offset. | `outline` + offset (≥ 2px), two-tone where surfaces vary, tested custom ring. |
| 38 | **Media vs container queries** | Shadeed: container queries. Comeau/Argyle: intrinsic, often no queries. M3: shell breakpoints 600/840/1200/1600. | Intrinsic first; container queries for components; media queries (M3 breakpoints) for the page shell and preferences. |
| 39 | **Dual-axis charts** | Datawrapper 2018, Knaflic, Few: avoid. Datawrapper 2026: acceptable with safeguards. | Avoid by default; only with every safeguard and a numerate audience. |
| 40 | **Chart baselines** | Few: bars from zero. Apple HIG Charts: bars from zero, but lines may use a non-zero baseline when differences sit far from zero. | Bars always from zero; lines may use a non-zero baseline, labelled clearly. |
| 41 | **Expressive vs restrained** | M3 Expressive: bolder is preferred and faster to scan. Few, Linear: subdued. Apple: tint only the primary action. | Emphasis is scarce: 1–2 hero moments per product, one primary per view. |
| 42 | **Icons vs labels** | Apple moves bars toward symbols. Google research: removing labels hurt usability. Apple HIG Toolbars: every icon item still has a title. | Icon-only only for universal glyphs, always with an accessible name and tooltip; otherwise label. |
| 43 | **Unavailable items: dim or hide** | Apple HIG Menus: dim in regular menus (discoverability). Apple HIG Context menus: hide (relevance). M3: hide an unavailable floating action. | Dim (with `aria-disabled`, still focusable) in menus and inline controls; hide in context menus and for floating actions. Not a source conflict; agents often flatten it. |
| 44 | **Time format** | Apple Style Guide (US): "8:30 a.m. PT". International style: ISO 8601, 24-hour. | Locale-formatted (`Intl.DateTimeFormat`) with an explicit time zone for scheduled times. |
| 45 | **Tab bar item count** | Apple HIG: 3–5 consumer tabs. Böhnke (Linear iOS): pro apps may exceed this if the bar expands to a sidebar. | 3–5 by default; more only for pro tools with an expanding tab bar → sidebar. |
| 46 | **Metrics vs judgement** | HEART, Torres: metric-driven. Linear: taste and customer insight, no A/B tests. | Define a success metric and a qualitative check; metrics inform taste. |
| 47 | **Effort in prioritisation** | Torres: ignore effort when choosing the opportunity. RICE: divide by effort. | Choose problems on value; rank solutions with effort. |
